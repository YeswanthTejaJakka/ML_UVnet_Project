1. ENVIRONMENT & EXECUTION ANALYSIS (LOCAL vs. DOCKER vs. GOOGLE COLAB)
--------------------------------------------------------------------------------
You asked whether it is advisable to run this project locally, if Docker should 
be used to avoid version conflicts, or if Google Colab is better, along with the 
drawbacks of each option (specifically loading times for data and models).

Here is a detailed technical trade-off breakdown:

A. OPTION 1: LOCAL SYSTEM (NATIVE WINDOWS BARE-METAL)
   - Verdict: NOT RECOMMENDED.
   - Why:
     1. UltraLight VM-UNet is built on Vision Mamba (Mamba-SSM). Mamba relies on 
        custom CUDA/C++ kernels (`mamba-ssm`, `causal-conv1d`, selective scan).
     2. Compiling and running these CUDA kernels natively on Windows is 
        notoriously difficult. It requires exact matches between Visual Studio 
        MSVC C++ build tools, CUDA Toolkit, and PyTorch versions, and frequently 
        fails with ninja build errors, C++ compiler symbol errors, and missing 
        Linux syscalls.
     3. It ties up your personal machine's GPU/CPU and risks environment corruption.

B. OPTION 2: LOCAL SYSTEM WITH DOCKER (DOCKER DESKTOP + WSL2)
   - Verdict: VIABLE BUT RESOURCE-HEAVY & PRONE TO LOCAL SETUP FRICTION.
   - Pros:
     1. Runs a Linux container (e.g., PyTorch CUDA base image), avoiding Windows 
        compilation bugs for Mamba-SSM.
     2. Eliminates package version conflicts and protects host system files.
     3. Local disk I/O is very fast once files are inside WSL2 ext4.
   - Drawbacks:
     1. Requires NVIDIA Container Toolkit configured on WSL2 with virtualization 
        enabled in BIOS.
     2. Heavy resource usage: Docker images with PyTorch + CUDA + Mamba can easily 
        exceed 18–25 GB of local SSD space.
     3. Dependent on having a sufficiently powerful local NVIDIA GPU (minimum 6–8 GB 
        VRAM recommended). If your laptop/desktop lacks an NVIDIA GPU or has low 
        VRAM, training will fail.

C. OPTION 3: GOOGLE COLAB (CLOUD GPU)
   - Verdict: STRONGLY RECOMMENDED.
   - Pros:
     1. Pure native Linux environment with free or paid access to NVIDIA GPUs 
        (T4, L4, V100, A100).
     2. Installing Linux Mamba wheels or compiling Mamba kernels on Colab is 
        streamlined and standard without Windows build headaches.
     3. Zero wear-and-tear or storage burden on your local machine.
   - Drawbacks & Exact Mitigations:
     1. Dataset Loading Bottleneck (The Common Trap):
        - The Drawback: If you connect Google Drive and load thousands of small 
          image and mask files directly through the mounted Google Drive 
          (`/content/drive/MyDrive/...`), training will be EXTREMELY SLOW. 
          Google Drive's FUSE file system imposes heavy read-latency on small files.
        - The Solution: Store the dataset as a SINGLE compressed file 
          (e.g., `TN3K.zip` or `TN3K.tar.gz`) in Google Drive. At the start of 
          the Colab session, copy the single archive into Colab's local scratch disk 
          (`/content/TN3K.zip`) and unzip it to `/content/TN3K/`. Unzipping takes 
          less than 15 seconds. After that, all training I/O runs on Colab's local 
          high-speed NVMe virtual disk with zero latency.
     2. Model Weight Loading:
        - UltraLight VM-UNet is extraordinarily lightweight: only ~0.049M parameters 
          (model checkpoint file size is only around 200 KB to 1 MB). Downloading 
          and loading model weights on Colab takes under 1 second.
     3. Session Timeouts / Disconnections:
        - Colab sessions can disconnect if idle, and free tiers cap continuous runs 
          at 12 hours.
        - The Solution: Configure automated checkpoint saving directly to 
          Google Drive after every epoch or when validation Dice improves, 
          along with resume-from-checkpoint capability.

SUMMARY RECOMMENDATION:
Use Google Colab (or Kaggle Notebooks as an alternative) using the zipped-data 
transfer workflow. We will develop clean, modular Python scripts locally (or in git) 
and run training and evaluation experiments smoothly on Colab.

2. COMPREHENSIVE PROJECT UNDERSTANDING
================================================================================

2.1 CONTEXT & CORE RESEARCH QUESTION
- Medical ultrasound imaging is notoriously susceptible to acoustic speckle noise, 
  low acoustic impedance contrast, fuzzy and irregular lesion boundaries, and 
  signal attenuation.
- Small lesions (e.g., small thyroid nodules) are especially difficult: standard 
  segmentation losses (BCE, Dice) treat all pixels equally or focus heavily on 
  bulk area overlap, causing the model to miss tiny lesions completely or generate 
  severely distorted boundary predictions.
- Central Research Question:
  "Can lesion-scale-aware boundary supervision combined with corruption-aware 
   consistency training improve small-lesion segmentation and boundary robustness 
   across ultrasound datasets (starting with TN3K thyroid ultrasound) without 
   increasing inference complexity?"

2.2 REVIEW AND ROLE OF THE 4 FOUNDATIONAL PAPERS
- Paper 1: UltraLight VM-UNet (Baseline Architecture)
  * Role: Our implementation baseline.
  * Characteristics: Ultra-compact parameter count (~0.049M parameters, ~0.060 GFLOPs) 
    using parallel Vision Mamba (VSS) blocks.
  * Key Insight: The model is already optimized for extreme parameter efficiency. 
    Our goal is NOT to add massive layers or complex inference branches, but to 
    enhance training loss and supervision dynamics so inference stays ultra-light.
- Paper 2: S³-Mamba (Small-Size-Sensitive Mamba for Lesion Segmentation)
  * Role: Conceptual guidance on lesion size sensitivity.
  * Key Insight: Small lesions degrade faster under downsampling and feature 
    aggregation. Provides guidance on how to define small lesion boundaries and 
    loss weightings based on lesion scale.
- Paper 3: FAViM (Frequency-Aware Vision Mamba for Ultrasound Segmentation)
  * Role: Benchmark and related work to clearly distinguish our novelty.
  * Key Insight: FAViM modifies architecture via frequency processing and boundary 
    scanning across breast, thyroid, and ovarian datasets. Our distinction: we keep 
    the model ultra-light without modifying inference architecture complexity, 
    focusing on scale-aware boundary distillation/supervision and speckle noise 
    consistency.
- Paper 4: BPKD (Boundary Privileged Knowledge Distillation)
  * Role: Methodological guidance for separating boundary and interior regions.
  * Key Insight: Decoupling boundary representation from internal mask pixels 
    during training allows the network to learn sharp edge details without 
    increasing testing overhead.

2.3 KEY HYPOTHESES & PROPOSED RESEARCH EXTENSIONS
The project investigates three synergistic components:
1. Lesion-Scale-Aware Boundary Supervision:
   - Extract lesion boundaries dynamically from ground truth masks during training 
     (e.g., using morphological operators / distance transforms / Laplacian filters).
   - Categorize lesions into scale bins (Small, Medium, Large) based on pixel area.
   - Dynamically weight boundary loss (e.g., weighted BCE/Dice/Boundary Loss) so that 
     small lesions receive higher boundary supervision intensity.
2. Corruption-Aware Consistency Training:
   - Simulate realistic ultrasound speckle corruption (Rayleigh-distributed speckle 
     multiplicative noise) and acoustic contrast degradation.
   - Apply a perturbation consistency regularization (e.g., MSE or symmetric KL 
     divergence on prediction logits between clean and corrupted versions of the 
     same image).
   - Forces the latent representations and boundaries to remain stable even when 
     speckle noise obscures edges.
3. Lightweight Deployment Guarantee:
   - The original UltraLight VM-UNet inference architecture remains 100% UNCHANGED.
   - Auxiliary boundary and consistency losses are active ONLY during training.
   - At test/deployment time, inference cost remains identical (~0.049M params, 
     ~0.060 GFLOPs, high FPS).

PHASE 4: DESIGNING & IMPLEMENTING PROPOSED RESEARCH EXTENSIONS (E2, E3, E4)
--------------------------------------------------------------------------------
Goal: Implement the novel training-time components with zero added inference cost.

Steps:
4.1 Component A: Lesion-Scale-Aware Boundary Supervision (E2):
    - Boundary Mask Generation: Compute ground truth boundary mask `B_gt` from mask `M_gt`.
    - Scale Factor Formulation: For each lesion, compute relative area `A = (sum(M_gt) / H*W)`.
      Compute scale weight: `w_scale = alpha * (1.0 / (A + epsilon))^gamma`, clipped to prevent 
      numerical explosion.
    - Auxiliary Boundary Head (Training Only): A single lightweight 1x1 conv projection head 
      predicting the boundary map during training.
    - Total Loss (E2): `L_E2 = L_seg(M_pred, M_gt) + lambda_b * w_scale * L_boundary(B_pred, B_gt)`.
    - In deployment/inference, this 1x1 boundary head is discarded; segmentation head output 
      is used directly.
4.2 Component B: Corruption-Aware Consistency Training (E3):
    - Speckle Corruption Engine (`corruptions.py`):
      * Multiplicative speckle model: `I_noisy = I + I * n`, where `n ~ Normal(0, sigma^2)` 
        or Rayleigh distribution.
      * Contrast attenuation: Dynamic gamma and sigmoid contrast shifts.
    - Consistency Loss:
      * Pass clean image `I` -> predictions `P_clean`.
      * Pass corrupted image `I_noisy` -> predictions `P_noisy`.
      * Compute Consistency Loss: `L_cons = MSE(P_noisy, P_clean)` or `KL(P_noisy || P_clean)`.
    - Total Loss (E3): `L_E3 = L_seg(P_clean, M_gt) + lambda_c * L_cons`.
4.3 Component C: Combined Framework (E4):
    - Full training objective uniting scale-aware boundary loss and corruption consistency.
    - Total Loss (E4): `L_total = L_seg + lambda_b * w_scale * L_boundary + lambda_c * L_cons`.
