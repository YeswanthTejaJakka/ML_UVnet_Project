Observed problems, each with the evidence that points to it:

1. **The model is under-trained, not over-fitted.** Final train seg-loss (BCE+Dice) is ≈0.50, which corresponds to a train Dice of only ≈0.65, the same as val Dice (≈0.68). Val Dice is still creeping up at epoch 50, and the cosine schedule hits `min_lr` exactly at epoch 50 because `T_max=epochs`. The configs say 150 epochs, but the notebook overrides them with `--epochs 50`. The official UltraLight VM-UNet recipe trains for far longer (verify the exact numbers in `wurenkai/UltraLight-VM-UNet`).
2. **The E1 vs E2/E3/E4 comparison is not controlled.** E1 is missing from the training-curve figure (its `training_log.csv` does not exist, so it was trained by an older version of `train.py` with an unknown protocol). The jump of +0.09 to +0.11 Dice from E1 to E2/E3/E4 is not explained by the methods: E3's consistency term has magnitude ≈0.003 against a seg loss of ≈0.5 (negligible gradient), and E2's boundary head is a single 1×1 conv with 9 parameters. E2, E3, E4 differ from each other by less than 0.02 Dice with one seed and one fold, which is within run-to-run noise (val Dice fluctuates ±0.01 between consecutive epochs). Conclusion: the current ranking cannot be trusted.
3. **About 1,000 of 2,879 trainval images are unused.** The log says `Train samples: 1503 | Val samples: 376` (= 1,879) while `trainval-image` has 2,879 files. `TN3KDataset._load_split_samples` silently skips any fold-JSON entry for which it cannot find both files (`if img_path and mask_path`). Either the fold JSON really lists only 1,879 images, or file matching is failing. This must be resolved first.
4. **The boundary supervision does not learn and dominates the loss.** In E4 the boundary term goes 1.89 → 1.02 (barely moves, so the boundary head predicts almost nothing useful) yet it is about two thirds of the total loss. It is a 1×1 conv on the same 8-channel final feature map, so it has almost no influence on the shared features. The scale weight `clip(1/(rel_area+1e-4)^0.5, 1, 5)` saturates at 5 for every lesion under ~4% of the image and sits between 1.8 and 5 for nearly all samples, so it hardly discriminates between sizes. E4 ends up *worse* than E3 on clean Dice, so the "proposed" method is not the best one.
5. **Consistency loss is numerically irrelevant.** MSE on probabilities with λ=1 gives ≈0.003. Its real effect in E3 is probably only an extra noisy forward pass. The robustness gain of E3 over E2 at σ=0.25 (0.652 vs 0.551) is real, but the loss is too weak to be the clean explanation, and there is no ramp-up or per-sample variation of the corruption.
6. **Failure mode is false-positive regions and merged nodules, not only boundaries.** Precision (0.69–0.71) is lower than recall (0.75–0.77). In the 8-case qualitative figure, E2–E4 produce large merged blobs when several nodules are present, extra spurious blobs, and under-segment large nodules. Pushing recall further (e.g. a recall-heavy Tversky loss) would make this worse. The model needs better global context/regularisation and cleaner training, not just sharper edges.
7. **Evaluation code has defects that make boundary metrics meaningless.**
   - `calculate_boundary_iou` uses `d0=2` px on 256×256 images. Cheng et al. use d ≈ 2% of the image diagonal (≈7 px at 256). With d=2 every model scores 0.03–0.05 and E2/E3/E4 are indistinguishable (0.0503 / 0.0512 / 0.0511).
   - `calculate_hd95` takes distances from **all pixels** of each mask (`dt_t[p]`, `dt_p[t]`) instead of **surface** pixels, so interior pixels contribute zeros and HD95 is under-estimated for large masks.
   - Metrics are computed on the 256×256 resized masks only.
   - Robustness covers only multiplicative speckle; the project spec also requires contrast changes.
   - `measure_model_efficiency` reports thop FLOPs, which do not count the SSM scan/einsum ops, and latency of the pure-PyTorch scan fallback (≈51–59 ms), not of the official Mamba CUDA kernel. These facts are not labelled in the report.
8. **Training curves are incomplete and not comparable.** `generate_deliverables.py` plots only `train_loss` and `val_dice`. E1 is missing. E3's "total loss" (no boundary term) is plotted on the same axis as E2/E4's total loss (which includes the boundary term of ≈1.0), so the curves cannot be compared. Train Dice/IoU, val loss, precision/recall, boundary loss, consistency loss, per-size Dice and LR are not logged or plotted, so over/under-fitting cannot be diagnosed.
9. **The qualitative figure is weak.** Eight cases are chosen by `np.linspace(0, N-1, 8)` over sorted filenames, shown as raw binary masks with no overlay, no per-case metric, and no selection logic. Several rows are failure cases with nothing explaining why. One ground-truth mask (a straight-edged block touching the left border) looks suspicious and must be checked for image/mask alignment.
10. **Numerical risks in the Mamba fallback.** Training runs under fp16 autocast. Inside `PyTorchMamba.forward`, `dA` is fp32 (exp autocasts to fp32) but `Bx` is fp16, and `PScan` does in-place `add_/mul_` across up to 1,024 tokens in mixed dtypes, which risks precision loss in the recurrent state. The model also outputs `sigmoid` probabilities in fp16 and then clamps for BCE, which saturates gradients. The custom `PScan.backward` has never been verified against a reference.
11. **Training is slow** (≈50 min per 50-epoch run, estimated from the checkpoint-backup timestamps), mainly because of per-step PIL decoding/resizing with 2 workers, `cudnn.deterministic=True`, and four sequential Mamba calls per PVM layer. This blocks the multi-seed runs needed for credible results.

### P4 — Loss redesign for the research components

**E2 — lesion-scale-aware boundary supervision (training-only, no extra inference cost)**

- New default `boundary_mode: from_mask`: derive the predicted boundary directly from the **main mask probability** with a differentiable morphological gradient (`dil = maxpool(p, k)`, `ero = -maxpool(-p, k)`, `b = dil - ero`, `k = 2r+1`), and compare it to the GT band with `r = 2` (5×5 kernel at 256 px). Loss = `Dice(b, gt_band) + BCE(b, gt_band)` with per-sample scale weights. This supervises the final contour directly and needs no extra branch. Keep the old auxiliary-head variant available as `boundary_mode: head` for the ablation, but make the head a 3×3 conv on the full-resolution decoder feature (training-only) rather than the current 1×1.
- New scale weight: `w_i = clip((A_ref / (area_i + eps))^γ, 1, w_max)` with `A_ref = 0.05`, `γ = 0.5`, `w_max = 4`, then **normalise to batch-mean 1** so the gradient scale does not change. Small lesions get the larger weight; lesions above 5% area get weight 1.
- `lambda_boundary` with a linear warm-up from 0 over the first 20% of epochs. Tune `λ ∈ {0.1, 0.3, 0.5}` on validation (single seed, 100 epochs). Log `λ·L_boundary / L_seg` and keep it ≤ 0.5 after warm-up.
- Add a switch `scale_aware_seg: true/false` that applies the same `w_i` to the per-sample BCE+Dice seg loss. Run it as an extra ablation (E2b); keep it only if it improves val small-lesion Dice without lowering overall val Dice.
- Do **not** add a recall-biased Tversky/focal loss to the main recipe (precision is already lower than it should be).

**E3 — corruption-aware consistency**

- Per-sample random corruption each step: `σ ~ U(0.05, 0.30)` multiplicative speckle (existing formula `I + I·η`), contrast factor `~ U(0.5, 1.0)`, optional Gaussian blur σ_blur `~ U(0, 1.0)` px.
- Consistency loss on the **soft masks**: `L_c = (1 − SoftDice(p_corrupt, stopgrad(p_clean))) + MSE(p_corrupt, stopgrad(p_clean))`. Soft-Dice is scale-invariant, so small lesions are not ignored (plain MSE on probabilities is dominated by background and was ≈0.003).
- `lambda_consistency` ramps up linearly from 0 over the first 20% of epochs. Tune `λ ∈ {0.5, 1, 2}` on validation. Log `λ·L_c / L_seg` and require it to be in 0.05–0.5 after warm-up (otherwise λ is too small to matter).
- Optional extra ablation E3+: also apply the supervised BCE+Dice loss (weight 0.5) on the corrupted view. Report it as a separate row. The main E3 stays "consistency only".

**E4 — combined**: E2-best and E3-best loss settings together, each at its own validation-tuned λ. If E4 does not beat max(E2, E3) on validation, still report it honestly and add one more tuning round of λ for the combination (small grid, validation only).

**Baselines to report side by side**
- **E1-orig**: faithful reproduction of the official UltraLight VM-UNet recipe (check the official repo for batch size, LR schedule, epochs, augmentation) with BCE+Dice and nothing else.
- **E1-R\***: baseline using the shared recipe from P3 (this is the fair reference for E2–E4).
